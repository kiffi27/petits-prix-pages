# API de boutique (en préparation)

Cette API Cloudflare Workers + D1 constitue le noyau serveur testable : elle publie uniquement les fiches actives en stock et vérifie les prix, le stock et le total côté serveur avant d’enregistrer une demande en attente. La réservation du stock et ses lignes sont exécutées dans un batch D1 ; un déclencheur SQL protège le stock contre les réservations concurrentes. Les tests exécutent le vrai handler et la migration avec SQLite intégré à Node et un adaptateur local du binding D1; ils ne remplacent pas une validation sur une base Cloudflare.

Avec Node.js 22.12 ou ultérieur, lancer `npm test` (aucune dépendance à installer). Wrangler lira le schéma dans `backend/migrations/`.

Le propriétaire indique que CinetPay a approuvé son compte de production et son modèle multi-boutiques, avec reversements manuels et commission de 1 %. Cette attestation ne signifie pas que les clés sont disponibles ou configurées dans cet environnement. L’accès Wrangler a été autorisé; la base D1 `petits-prix-orders` a été créée en région WEUR et les migrations `0001_store.sql` et `0002_product_shop.sql` ont été appliquées. Le Worker est déployé sur `https://petits-prix-orders.petits-prix.workers.dev`, avec les URL de prévisualisation désactivées. La page statique est configurée pour interroger cet endpoint. Le catalogue distant reste vide, `STORE_ENABLED` et `ORDERS_ENABLED` sont à `false`, et les tests en direct confirment que les routes catalogue et commandes répondent « désactivé » (HTTP 503).

Le Worker exige le binding Cloudflare Rate Limiting pour toute requête; il utilise la valeur `CF-Connecting-IP` comme clé et ne l’enregistre pas dans D1. La limite est pondérée (100 unités par 60 secondes et par adresse/lieu Cloudflare; une requête POST en consomme 10) et reste approximative, locale à chaque lieu Cloudflare. Les adresses partagées peuvent donc partager une limite. Cette protection est une base, pas une limite globale stricte ni un remplacement d’une surveillance/WAF. Le site public interroge le Worker pour le catalogue; le Worker garde les routes catalogue et commandes fermées jusqu’à activation explicite.

## CinetPay — préparation Sandbox seulement

`backend/cinetpay.js` prépare une initialisation de test en suivant l’API v1 documentée dans le dépôt officiel [`CinetPay/cinetpay-seamless`](https://github.com/CinetPay/cinetpay-seamless) : OAuth `/v1/oauth/login`, puis initialisation `/v1/payment`. La clé est limitée par code au préfixe `sk_test_`, l’environnement doit être explicitement `sandbox` et les URL de retour/notification doivent être HTTPS. La réponse ne peut fournir qu’une URL HTTPS des domaines CinetPay. Aucun statut reçu du navigateur ne confirme un paiement.

Ce module est couvert par des tests avec un faux transport HTTP; il n’effectue aucune requête à CinetPay et n’utilise aucun vrai compte. Il n’est appelé par aucune route Worker : l’initialisation, les webhooks et la vérification distante du statut ne sont pas encore branchés. Aucune clé, aucun mot de passe API et aucun identifiant de compte n’est inclus ou demandé dans le chat. Avant un test Sandbox réel, les identifiants de test et URL serveur doivent être configurés comme secrets Cloudflare, jamais comme variables publiques. La production est impossible dans ce module : n’ajoutez pas de clés production et n’élargissez pas son mode sans approbation explicite.

L’assistance CinetPay fournie indique un paiement marketplace sans split ni escrow natif : la plateforme marchande doit calculer la commission et les montants à reverser. Elle indique aussi une disponibilité des fonds après 7 jours et des frais indicatifs de 2,5 % Pay-in et 2 % Payout, plus d’éventuels frais; le montant exact et les modalités de retrait du compte restent à valider. Ces frais prestataire sont distincts de la commission de 1 % que le propriétaire indique avoir fait approuver.

Le client accepte uniquement une URL HTTPS configurée dans la balise `meta[name="store-api-url"]`; elle pointe vers l’endpoint ci-dessus. Il n’affiche aucune fiche illustrative ou inventée. Les produits doivent avoir un nom de boutique; la migration en conserve aussi une copie dans chaque ligne de commande. Les commandes restent séparément bloquées par `ORDERS_ENABLED=false`; les commandes multi-boutiques sont refusées par le Worker. Le contact client, la livraison, l’annulation/remboursement et l’exploitation des commandes ne sont pas définis. Ne pas ouvrir les commandes avant ces validations. CinetPay Sandbox reste non branché; aucun paiement réel n’est possible.
